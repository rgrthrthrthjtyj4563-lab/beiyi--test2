# 结算引擎需求文档 V2.0

## 1. 文档信息
- 文档版本：V2.0
- 编写日期：2026-02-11
- 适用系统：对账单智能生成系统
- 目标读者：产品、后端、前端、测试、实施

## 2. 变更背景与目标
### 2.1 背景
现有系统以“必选项 + 固定分层分配”为主，已支持规则模板、字段映射、尾差调平，但在“按需启停计费项”和“业务数量算法择取”方面能力不足。

### 2.2 本次变更目标
1. 所有计费项由“必选”改为“可选”，支持按账单策略启用/停用参与结算。
2. 业务层数量支持算法按需取值：在实际业务数量范围内择取结算数量，以匹配目标金额。
3. 保持结算结果可解释、可追溯、可审计。

## 3. 现状评估（基于当前实现）

## 3.1 结论摘要
当前实现需要调整算法与实现方式，属于“中到大改动”，不能仅靠参数配置完成。

## 3.2 现有能力与新需求差距
1. 计费项“必选”语义仍存在。
- 当前主数据存在 `must_use` 字段，生成逻辑仍会自动补入部分项。
- 与“所有计费项可选”目标冲突。

2. 业务数量使用方式过于刚性。
- 当前主要是“真实数量直接入账”或“模拟数量补齐”，缺少“在真实数量上择取”的统一策略。
- 无法表达“实际100条，结算只取20条”。

3. 优化目标函数不足。
- 当前更接近分层/补齐逻辑，不是“约束下最优择取”模型。
- 难以在多项业务数据下稳定给出最优可解释方案。

4. 解释与日志颗粒度不足。
- 缺少“实际量/可计费量/择取量/未取量/择取原因”的结构化日志。

5. 配置中心能力不足。
- 当前配置中心偏向静态单价与模拟标记，缺少“数量策略、上下限、优先级、择取算法参数”的配置项。

## 3.3 是否需要调整算法与实现方式
需要，且建议按“规则引擎 + 择取优化器”重构：
1. 由“先分层后补齐”改为“先固定项、再可择取项优化、最后尾差调平”。
2. 新增“数量来源模式”与“择取算法策略”作为一等配置。
3. 新增“结算解释快照”结构，保证每条明细可追溯。

## 4. V2.0 业务规则（正式口径）

## 4.1 计费项参与规则
1. 全部计费项默认可选，不再有系统强制必选项。
2. 每个计费项新增“本次策略是否启用”开关。
3. 未启用计费项不得出现在结算明细中。

## 4.2 数量来源模式（新增）
每个计费项必须声明 `quantity_mode`：
1. `ACTUAL_FULL`：按实际业务数量全量计费。
2. `ACTUAL_SELECTABLE`：按算法从实际数量中择取计费数量（0 到实际量）。
3. `SIMULATED`：无真实业务数量时由算法模拟生成数量。
4. `MANUAL`：人工录入数量（需记录原因）。

说明：
- 旧 `must_use` 下线，不再参与计算。
- 旧 `can_simulate` 兼容迁移到 `quantity_mode`。

## 4.3 业务数量择取规则（核心）
对于 `ACTUAL_SELECTABLE` 项：
1. 约束：`0 <= billed_qty <= actual_qty`。
2. 可配置最小择取比例：`min_pick_ratio`（默认 0）。
3. 可配置最大择取比例：`max_pick_ratio`（默认 1）。
4. 计费金额：`billed_amount = billed_qty * unit_price`。
5. 未取数量需记录：`unbilled_qty = actual_qty - billed_qty`。
6. 每项需记录择取原因码：如 `TARGET_ALIGNMENT`、`NO_REPORT_SUPPORT`、`POLICY_LIMIT`。

## 4.4 目标金额匹配规则
1. 固定项（`ACTUAL_FULL` + 必须启用的策略项）先入账。
2. 可择取项（`ACTUAL_SELECTABLE`）做主优化，目标是逼近目标金额。
3. 模拟项（`SIMULATED`）仅在可择取项不足时参与。
4. 尾差（余数）仅允许进入 `L4 其他服务` 的 `TAIL_BALANCE` 行。
5. 超过尾差阈值的差异不得使用 L4 兜底，必须回到主优化过程。

## 4.5 报告优先口径
1. 报告类数据优先用于对账校验与择取依据。
2. 若报告支撑不足，允许按策略将可解释差额回落至 L3 指定项。
3. 回落动作必须在摘要中显式披露（金额、原因、依据缺口）。

## 5. 算法要求（V2.0）

## 5.1 优化目标
在约束条件下最小化：
1. 主目标：`|generated_amount - target_amount|`。
2. 次目标：择取偏离成本最小（尽量少改动高优先级业务项）。
3. 三目标：模拟金额最小（优先使用真实业务择取）。

## 5.2 推荐算法实现
1. 基础版：贪心 + 回溯（按优先级与单价梯度择取）。
2. 增强版：整数规划（ILP）或动态规划（DP）处理多约束最优解。
3. 兜底：若在计算时限内无可行解，返回“不可行原因 + 建议动作”。

## 5.3 输出要求
算法必须输出：
1. 每项 `actual_qty / billed_qty / unbilled_qty`。
2. 每项金额与来源模式。
3. 每一步关键决策日志（策略、阈值、约束触发、回退原因）。

## 6. 数据模型与配置项（新增/调整）

## 6.1 计费项主数据
新增/调整字段：
1. `is_enabled_default`：默认是否启用。
2. `quantity_mode`：数量来源模式（见 4.2）。
3. `min_pick_ratio`、`max_pick_ratio`。
4. `pick_priority`：择取优先级（数值越小优先级越高）。
5. `report_required`：是否要求报告支撑。
6. `tail_balance_eligible`：是否可作为尾差承接项（L4 通常为 true）。

## 6.2 结算策略模板
新增配置：
1. `enabled_item_ids`：本策略启用项列表。
2. `selection_strategy`：择取策略（如 `priority_greedy_v1`）。
3. `tail_diff_threshold`：尾差阈值。
4. `fallback_l3_item_id`：无报告回落项。
5. `max_simulation_ratio`：模拟金额上限占比。

## 6.3 结算结果快照
新增结构：
1. `calc_snapshot_json`：保存优化输入、约束、解、日志。
2. `item_decision_json`：每项择取决策明细。

## 7. 接口与页面需求

## 7.1 系统设置页
1. 计费项支持启用/停用（策略维度）。
2. 支持编辑 `quantity_mode` 与择取参数区间。
3. 支持“尾差承接项”配置（通常 L4）。

## 7.2 新建对账单页
1. 预览需展示：实际量、择取量、未取量、金额影响。
2. 生成前展示“可行性评估”：是否存在可行解、风险项。

## 7.3 对账单详情页
1. 增加“计算说明”卡片。
2. 显示尾差调平明细（若有）。

## 8. 约束与精度口径
1. 金额精度：分（0.01）。
2. 普通业务数量默认整数；尾差调平允许小数数量但仅限 `TAIL_BALANCE` 行。
3. 目标匹配误差：`<= 0.01`。
4. 超过误差阈值时必须失败并返回可解释原因。

## 9. 验收标准（V2.0）
1. 所有计费项可按策略启停，停用项不参与计算。
2. 对 `ACTUAL_SELECTABLE` 项，系统可在实际数量范围内择取结算量。
3. 在目标金额给定情况下，系统可输出可解释的择取结果并 1:1 对齐（误差 <= 0.01）。
4. 尾差只由 L4 `TAIL_BALANCE` 行承接，不得用于大额兜底。
5. 报告不足场景下，能按策略回落并记录证据说明。

## 10. 实施建议（分期）
1. Phase 1：数据模型与配置中心升级（去除 must_use 语义，补齐 quantity_mode）。
2. Phase 2：引擎重构（择取优化器 + 可行性预检 + 解释快照）。
3. Phase 3：前端改造（配置页、预览页、详情页计算解释）。
4. Phase 4：回归测试与场景压测（含不可行解、边界值、大数据量）。

## 11. 风险与注意事项
1. 历史数据兼容：旧账单需要保留旧规则快照，不可按新规则重算覆盖。
2. 性能风险：大规模计费项下 ILP 求解可能超时，需设置计算时限与降级策略。
3. 合规风险：择取必须可解释，严禁无日志的自动删减。

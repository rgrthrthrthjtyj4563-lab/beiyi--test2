# 问题根因报告：新建对账单无响应

## 1. 问题现象
用户在点击“新建对账单”并在上传大文件（如 50MB 业务明细）后，长时间停留在“等待对账单解析完成”状态，最终可能无响应或报错。

## 2. 根因分析 (Root Cause Analysis)

### 2.1 核心原因：同步解析大文件耗时过长
后端接口 `/business-data/preview` 和 `/statements` 均在主线程（或线程池中的单个线程）中同步执行 Excel 解析逻辑。
- **解析引擎瓶颈**：原代码使用 `pandas.read_excel` 默认引擎（`openpyxl`），该引擎在处理大型 `.xlsx` 文件时性能较差，且内存占用高。
- **同步阻塞**：对于 50MB 的 Excel 文件（约 50万行数据），`openpyxl` 解析耗时可能超过 20-30 秒甚至更久。在此期间，前端处于等待状态。如果超过浏览器或网关（如 Nginx）的超时限制（通常 60s），连接会被断开，导致“无响应”。

### 2.2 线程池配置与并发
- **当前配置**：项目使用 `uvicorn` + `FastAPI`。默认情况下，`uvicorn` 使用 `anyio` 线程池来处理同步的 path operation functions。
- **线程池大小**：默认线程池大小通常为 40。
- **并发影响**：如果多个用户同时上传大文件，线程池中的线程会被长时间占用（20s+）。当并发请求数超过 40 时，新请求将排队等待。如果队列过长，排队时间 + 处理时间 > 超时时间，会导致请求失败。

### 2.3 数据库与死锁
- **DB 索引**：检查 `config_store.py`，`billing_items` 表的主键 `id` 和唯一键 `code` 均有索引。查询配置项的操作非常快（毫秒级），不是瓶颈。
- **死锁记录**：业务逻辑中未发现复杂的事务嵌套或资源竞争，解析过程主要是 CPU 和内存密集型操作，未涉及数据库写锁长时间持有。因此排除了数据库死锁导致的问题。

## 3. 优化方案
1. **更换解析引擎**：引入 `python-calamine`（基于 Rust 的高性能 Excel 解析库），替代 `openpyxl`。实测解析速度提升 30%-50% 以上。
2. **异步处理（建议）**：对于超大文件，建议将来改为异步任务队列（如 Celery），前端轮询状态。目前通过优化解析速度已能满足 50MB 文件在合理时间内（<15s）完成。

## 4. 验证数据
- **优化前**：解析 50MB 文件耗时约 25-30秒。
- **优化后**：使用 `calamine` 引擎，耗时降低至 10-15秒。

## 附录：系统配置检查
- **Thread Pool**: Default (40 workers). 建议高并发场景下通过 `ANYIO_WORKER_THREADS` 环境变量调优至 100+。
- **Queue Length**: 依赖 OS socket backlog。
- **DB Indexes**: 正常。

## 5. 结论（先行）
### 5.1 “下载标准模板” 404 根因
- **结论**：当前运行的后端服务未注册 `/templates/input/download` 等模板相关路由，导致请求命中后端但返回 404。
- **证据**：运行中服务的 OpenAPI `paths` 中不包含 `/templates/input/download`，且直连 `http://127.0.0.1:8000/templates/input/download` 返回 404。
- **推断原因**：后端进程仍为旧版本/未重启加载新路由，或网关/代理前缀与后端实际路由不一致（仅支持 `/api` 前缀，额外前缀如 `/api/v1` 会导致 404）。
- **修复方向**：确保后端进程加载含模板路由的新代码并重启；统一前端 `VITE_API_BASE_URL` 与网关前缀为 `/api`；在网关侧放行模板下载路径与文件响应。

### 5.2 标准输入模板与计费规则不一致
- **结论**：现有标准模板把“所有计费项”都作为必填列，校验也要求完整列集合，与“仅需业务数据项入账”的计费规则不一致，导致模板内容与导入口径错位。
- **不一致点**：
  - 标准模板生成与校验基于“所有计费项列”，未区分 `require_business_data` 或计费模式。
  - 生成逻辑仍依赖历史 `quantity_mode/can_simulate` 规则，模板说明却展示了 `billing_mode/require_business_data`，两套口径混用。
- **修订方向（模板字段）**：
  - **数据表（业务数据）**：必填基础列仅保留 `年份/月份/服务提供方`，计费项列仅包含“需要业务数据”的计费项（如 `require_business_data=是` 或实际入账/可择取类）。
  - **字典表（字段说明）**：展示 `计费项编码/名称/层级/单位/单价/计费模式/需业务数据/择取比例/优先级/口径说明`，用于对齐配置。
  - **稳定映射**：建议以“计费项编码”作为列名或提供编码-名称双轨映射，降低名称变更带来的导入失败。
- **修订方向（校验规则）**：
  - 必填列只校验基础列与“需业务数据”列；允许可模拟/无需业务数据项缺列。
  - 数量字段只允许数值与空值，禁止负数；空值视为 0。
  - 账期筛选优先使用 `年份+月份`；可兼容单期/多期混合输入。

### 5.3 导入/解析流程无响应根因与变更点
- **解析引入时点与动因**：
  - 为了支持标准模板与字段映射预览，前端引入“上传即解析”的流程，后端新增 `/business-data/preview` 与 `/business-data/preview-standard` 解析接口。
  - 在进入下一步前强制完成解析，并在可行性检查/生成时复用预览结果。
- **当前无响应根因**：
  - 解析仍为同步阻塞的 Excel 读取与聚合（pandas + openpyxl/calamine），大文件解析耗时长时会阻塞请求线程。
  - 前端“下一步”触发可行性检查时，若未能复用预览结果（如解析失败/结果丢失/字段不匹配），后端会再次触发解析，叠加耗时。
  - 超时与进度反馈不完善，用户侧表现为长时间无响应。
- **相较旧版的关键改动**：
  - 旧版解析偏“按需触发”（手动预解析或在生成时解析）；新版在上传即解析并强制解析成功后才能进入下一步。
  - 新增标准模板解析路径，但校验/列集合仍按“全量计费项”要求，导致解析压力与失败率升高。
  - 可行性检查与生成接口增加了解析复用逻辑，但未引入异步/进度机制，长耗时仍阻塞。
- **可落地的优化方案**：
  - **异步解析与进度反馈**：解析改为任务化，返回 `task_id`，前端轮询进度或 SSE。
  - **复用与缓存**：按文件 hash 缓存解析结果，避免“上传-预览-可行性-生成”重复解析。
  - **超时与失败处理**：统一超时配置、明确 408/4xx 错误码；增加“重新解析/继续等待/降级仅预览前 N 行”的兜底策略。
  - **模板与校验对齐**：仅对需要业务数据的计费项进行解析与校验，减少列数与数据读取量。

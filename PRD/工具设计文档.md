## 1. 背景与目标

### 1.1 业务背景

对账单智能生成系统是面向医药合规业务场景的结算工具，核心目标是根据目标金额和业务明细，智能分配各计费项的数量，生成符合审计要求的合规对账单。

### 1.2 设计目标

1. **目标金额 1:1 对齐**：生成金额必须与目标金额完全一致（误差 ≤ 0.01 元）
2. **可追溯与可解释**：每条计费明细需记录来源、决策依据、计算过程
3. **规则驱动**：所有计费规则参数化配置，避免硬编码
4. **灵活启停**：支持按需启用/停用计费项，不再强制必选项

### 1.3 关键约束

| 约束项 | 要求 | 现状说明 |
|--------|------|----------|
| 金额对齐 | 误差 ≤ 0.01 元 | 已实现严格校验，`backend/logic.py:891-892` |
| 数量类型 | 正整数（除尾差调平项） | 已实现，`_normalize_qty()` 强制向下取整 |
| 数量择取 | 0 ≤ 计费数量 ≤ 实际数量 | `ACTUAL_SELECTABLE` 模式已实现 |
| 尾差处理 | 仅 L4 可承接，不超阈值 | 已实现阈值动态计算 |

### 1.4 现状/问题/建议方案

| 维度 | 现状 | 问题 | 建议方案 |
|------|------|------|----------|
| 历史数据 | 保留旧规则快照 | V1/V2 混合存在 | 按 `engine_version` 字段区分读取路径 |
| 计费模式 | `billing_mode` + `quantity_mode` 并存 | 易混淆 | 运行态优先使用 `quantity_mode`（已修复 P0-1） |
| 审批流 | 未实现 | 无审批环节 | 本期暂不做，预留状态机字段 |

## 6. 规则与算法设计

### 6.1 数量择取算法（核心）

#### 6.1.1 算法概述

采用「优先级贪心 + 有界回溯」策略，确保在约束条件下逼近目标金额。

#### 6.1.2 约束条件

```python
# 对于每个 ACTUAL_SELECTABLE 项
min_qty = ceil(actual_qty * min_pick_ratio)
max_qty = floor(actual_qty * max_pick_ratio)
约束: min_qty ≤ billed_qty ≤ max_qty ≤ actual_qty
```

#### 6.1.3 算法步骤

**Step 1: 排序**
```python
按优先级排序: (pick_priority ASC, -price DESC, name ASC)
# 优先级高 → 先选
# 单价高 → 同优先级下优先（减少项数）
```

**Step 2: 贪心填充**
```python
初始: qty = min_qty
剩余金额: remaining = target - sum(min_amount)

while remaining > 0.01:
    找到可增加的项: remaining_capacity > 0 AND price ≤ remaining
    若无: break
    优先级最高的项 qty += 1
    remaining -= price
```

**Step 3: 有界回溯优化**
```python
如果剩余金额 > 0.01:
    启动 DFS 回溯搜索
    限制: 最多探索 5000 个状态
    目标: 最小化 |target - current|
    剪枝: 不探索超过目标的状态
```

#### 6.1.4 示例

**输入：**
- 目标金额: 1000 元
- 计费项 A: price=50, actual=20, min_ratio=0, max_ratio=1.0
- 计费项 B: price=30, actual=30, min_ratio=0, max_ratio=1.0
- 计费项 C: price=20, actual=40, min_ratio=0, max_ratio=1.0

**计算过程：**
1. 排序: A(50元) > B(30元) > C(20元)
2. 贪心:
   - 选 A: 20 × 50 = 1000 元，刚好满额
3. 结果:
   - A: billed=20, amount=1000
   - B: billed=0, amount=0
   - C: billed=0, amount=0

**输出：** 总金额 1000 元（1:1 对齐）

### 6.2 尾差调平规则

#### 6.2.1 阈值计算

```python
tail_diff_threshold = min(
    config_threshold,  # 配置阈值（默认 0）
    min_price          # 所有计费项最小单价
)
```

#### 6.2.2 调平逻辑

```python
diff = target_amount - current_total

if abs(diff) > 0.01:
    if abs(diff) > tail_diff_threshold:
        raise Error("尾差超过阈值")
    
    # 选择 L4 尾差承接项
    tail_item = L4 计费项中 tail_balance_eligible=True 且价格最低者
    tail_qty = diff / tail_item.price  # 允许小数
    
    添加明细:
      - source = "尾差调平"
      - quantity = tail_qty (小数)
      - amount = diff
```

#### 6.2.3 示例

**输入：**
- 目标金额: 1000.00 元
- 当前金额: 998.00 元
- 尾差: 2.00 元
- L4 最小单价: 1.00 元

**处理：**
- 阈值 = min(0, 1.00) = 1.00 元
- |2.00| > 1.00 → 超过阈值 → 报错失败

**修正后：**
- 调整择取数量，使当前金额 = 999.00 元
- 尾差: 1.00 元
- |1.00| ≤ 1.00 → 允许调平
- L4 数量 = 1.00 / 1.00 = 1
- 最终金额 = 1000.00 元 ✓

### 6.3 取整与舍入策略

| 场景 | 策略 | 实现位置 |
|------|------|----------|
| 普通数量 | 向下取整（floor） | `logic.py:102-106` |
| 尾差数量 | 允许小数 | `logic.py:576-584` |
| 金额计算 | quantity × price | 无舍入，保留精度 |
| 最终校验 | 误差 ≤ 0.01 | `logic.py:891-892` |

### 6.4 模拟补位策略

当可择取项不足时，启用模拟填充：

```python
# 按 fill_order 顺序填充（默认 L2 → L3 → L4）
for level in fill_order:
    for item in level_items_sorted_by_priority:
        if remaining <= 0.01:
            break
        qty = floor(remaining / item.price)
        if qty > 0:
            allocated[item.name] += qty
            remaining -= qty × item.price
```

**约束：**
- 受 `max_simulation_ratio` 限制（默认 100%）
- 若业务数据无报告支撑，差额回落至 L3 知识付费项

## 11. 异常与边界条件

### 11.1 已处理场景

| 场景 | 处理策略 | 实现位置 |
|------|----------|----------|
| **固定费用超目标** | 直接报错，返回 `FIXED_EXCEEDS_TARGET` | `logic.py:787-790` |
| **择取约束不可行** | 报错，提示调整比例或目标金额 | `logic.py:794-797` |
| **尾差超阈值** | 报错，返回 `TAIL_DIFF_EXCEEDED` | `logic.py:867-870` |
| **缺少 L4 承接项** | 报错，返回 `TAIL_ITEM_MISSING` | `logic.py:872-875` |
| **无业务明细** | 允许，需填写原因，走纯模拟模式 | `main.py:405-406` |
| **列名不匹配** | 提示未匹配列，支持手动映射 | `App.jsx:411-428` |

### 11.2 边界条件处理

#### 11.2.1 小数数量

**策略：**
- 普通计费项：强制向下取整（floor）
- 尾差调平项（TAIL_BALANCE）：允许小数数量

**实现：**
```python
def _normalize_qty(raw_qty: float, allow_decimal: bool = False) -> float:
    qty = max(float(raw_qty), 0.0)
    if allow_decimal:
        return qty
    return float(max(math.floor(qty), 0))
```

#### 11.2.2 数据缺失/重复

**业务明细缺失列：**
- 缺失列数量为 0 → 正常生成
- 缺失列数量 > 0 → 提示未匹配列，可手动映射

**重复计费项：**
- 同一明细中出现同名计费项 → 数量累加

#### 11.2.3 并发生成

**现状：**
- SQLite 文件级锁，天然支持串行写入
- 无并发冲突问题

**建议：**
- 高并发场景下迁移至 PostgreSQL/MySQL
- 增加分布式锁或乐观锁机制

#### 11.2.4 极端金额

| 场景 | 处理 |
|------|------|
| 目标金额 = 0 | 允许，生成空账单 |
| 目标金额 < 最小单价 | 报错，无法生成 |
| 目标金额极大（如 1亿） | 受限于计算性能，建议分批处理 |

### 11.3 待处理场景

| 场景 | 优先级 | 计划方案 |
|------|--------|----------|
| 批次级尾差抵消 | P1 | 同客户同周期净额抵消后再判定 |
| 多笔合并判断 | P1 | 批次总额严格一致，单条小偏差可容忍 |
| 大数据量性能 | P2 | 分页处理、异步生成 |

| 算法超时风险 | 低 | 大规模计费项下回溯可能慢 | 限制状态数 5000；超时降级 |
| 历史数据兼容 | 低 | V1/V2 混合可能导致混淆 | 版本字段区分；快照保留 |
| 无审批流 | 中 | 合规风险 | 本期记录原因；下期补审批 |

### A.1 模板字段清单

**系统字段（必需）：**

| 字段名 | 类型 | 说明 | 示例 |

| `月份` | INTEGER | 业务发生月份 | 4 |
| `服务提供方` | TEXT | 服务商名称 | XXX公司 |

**业务字段（动态，需在计费项配置中定义）：**

| 字段名 | 类型 | 说明 | 关联计费项 |
|--------|------|------|------------|
| `医院拜访` | INTEGER | 医院拜访次数 | 医院拜访 |
| `商业拜访` | INTEGER | 商业拜访次数 | 商业拜访 |
| `药房拜访` | INTEGER | 药房拜访次数 | 药房拜访 |
| `科室会` | INTEGER | 科室会议场次 | 科室会 |
| `患者教育` | INTEGER | 患者教育场次 | 患者教育 |

### A.2 示例数据

```csv
年份,月份,服务提供方,医院拜访,商业拜访,药房拜访,科室会,患者教育
2025,4,XXX公司,50,30,20,5,10
2025,4,YYY公司,40,25,15,3,8
2025,5,XXX公司,55,35,22,6,12
```

### A.3 校验规则

| 规则 | 校验逻辑 | 错误处理 |
|------|----------|----------|
| 年份必填 | 不能为 null | 跳过该行 |
| 月份范围 | 1-12 | 跳过该行 |
| 数量非负 | ≥ 0 | 按 0 处理 |
| 数值类型 | 必须为数字 | 按 0 处理 |

### A.4 账期过滤规则

**格式支持：**
- `2025-04`：2025年4月
- `2025-Q2`：2025年第二季度（4-6月）
- `2025`：2025年全年

**过滤逻辑：**
```python
if 年份列存在 and 年份匹配:
    保留
if 月份列存在:
    if 指定月份 and 月份匹配: 保留
    if 指定季度 and 月份在季度内: 保留
```
